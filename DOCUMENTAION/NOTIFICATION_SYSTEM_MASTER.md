# German Learning App --- Notification System Master Documentation

## Purpose

The German Learning App has a personal push-notification system for
daily Wortschatz reminders.

The system is designed to be: - minimal in stored data; - anonymous (no
email/password account); - multi-user; - multi-device; - controlled by
the user; - based on Cloudflare Worker + KV + Web Push.

------------------------------------------------------------------------

## 1. Architecture

### Client

The German Learning App is a PWA.

Relevant app parts: - Home - Wortschatz - Service Worker for Web Push

### Backend

Cloudflare Worker:
`german-learning-notifications.d45zgw2cgh.workers.dev`

Repository: `OxReD112/der-die-das`

Backend folder: `notification-server/`

Main Worker: `notification-server/src/index.js`

Configuration: `notification-server/wrangler.jsonc`

### Storage

Cloudflare KV binding: `GERMAN_NOTIFICATION_STATE`

The Worker stores only the state required for notifications.

### Delivery

Web Push / VAPID is used to deliver notifications to iOS devices.

## 2. User and Device Model

There is no email/password authentication.

Each installation has: - `userId` - `deviceId`

The intended architecture supports multiple devices per user.

Important distinction: - `userId` identifies the user's notification
state. - `deviceId` identifies an individual device/subscription.

Each user has independent: - notification ON/OFF state; - daily pool; -
DONE state; - push subscriptions.

One user's DONE/OFF state must never affect another user.

Multiple devices belonging to the same user can receive the same
scheduled notification.

------------------------------------------------------------------------

## 3. Notification Schedule

The Worker Cron runs every 30 minutes.

Actual notification slots are only:

-   09:30
-   12:30
-   18:00
-   20:00

Timezone: `Europe/Berlin`

The Cron must not send notifications at other times.

Missed slots are NOT sent retroactively.

Example: If the 12:30 notification was missed, the 12:30 notification is
not sent later at 14:00.

------------------------------------------------------------------------

## 4. Notification Pool

Wortschatz prepares a pool for the next day.

Maximum pool size: 4 notifications.

Pool rules:

-   0 items → no notifications.
-   1 item → `1, 1, 1, 1`
-   2 items → `1, 2, 1, 2`
-   3 items → `1, 2, 3, 1`
-   4 items → `1, 2, 3, 4`

The Worker uses the scheduled slot index to select the corresponding
pool item.

The pool is stored per user and date:

`pool:<userId>:<date>`

The server must not use one global pool for all users.

------------------------------------------------------------------------

## 5. DONE Logic

When the user finishes the current day's Wortschatz:

1.  The app sends DONE for today's date.
2.  The Worker stores: `done:<userId>:<date>`
3.  Remaining notifications for that day stop.
4.  The app prepares the pool for the next day.

If the user finishes after the 20:00 slot, there are no more
notifications that day.

DONE is user-specific.

DONE on one device stops scheduled notifications for that user,
including the user's other registered devices.

------------------------------------------------------------------------

## 6. Notifications ON/OFF

Notifications are OFF by default.

The user must explicitly enable them.

The ON/OFF state is persistent. It is a user setting, not a daily
learning status.

### ON

-   The user enables notifications in Home.
-   The app registers the push subscription.
-   The Worker stores the subscription.
-   The Worker enables scheduled notifications for that user.

### OFF

-   The user disables notifications in Home.
-   The Worker disables scheduled notifications.
-   Existing pool and push subscription are kept.

Turning OFF does not delete the pool.

Turning ON again resumes the existing notification system.

There is no catch-up after a period when notifications were OFF.

------------------------------------------------------------------------

## 7. Final Push Format

The final notification format is intentionally fixed.

Title:

`Hallo`

Body:

`German sentence` `Russian translation`

The two body lines are separated by a newline:

``` text
German sentence
Russian translation
```

Example:

Title: `Hallo`

Body:

``` text
Ich lerne heute Deutsch.
Сегодня я учу немецкий.
```

On iOS, the system additionally displays:

`from Deutsch`

This is generated by iOS and is not controlled by the Worker.

The Worker payload uses:

``` js
{
  title: "Hallo",
  body: `${notification.de}
${notification.ru}`,
  icon: "/icon.png",
  badge: "/icon.png",
  tag: "german-learning-notification",
  url: "/"
}
```

The title/body format is shared by the real scheduled push path.

------------------------------------------------------------------------

## 8. Multi-device Behavior

Example:

User A has: - iPhone - iPad

Both devices have the same `userId` but different `deviceId`s.

Both devices can have their own Web Push subscription.

At a scheduled time: - Worker finds User A; - checks User A's ON/OFF
state; - checks User A's DONE state; - gets User A's pool; - sends the
selected notification to each registered device subscription.

If User A finishes Wortschatz: - both devices stop receiving remaining
notifications for that day.

If User A turns notifications OFF: - both devices stop receiving
scheduled notifications.

Another user's state is unaffected.

------------------------------------------------------------------------

## 9. Important KV Key Structure

Conceptual keys:

``` text
users:index

enabled:<userId>

subscription:<userId>:<deviceId>

pool:<userId>:<date>

done:<userId>:<date>
```

`users:index` contains only anonymous user IDs so the Cron can iterate
through registered users.

## 13. Important Development Rules

### Do not change the notification architecture casually

The current architecture is already working.

Before changing notification behavior, preserve: - user isolation; -
device-specific subscriptions; - user-specific pool; - user-specific
DONE; - persistent ON/OFF; - fixed Berlin schedule; - no catch-up
behavior.

### Do not introduce accounts unnecessarily

The current system intentionally uses anonymous IDs rather than
email/password.

### Keep notification content minimal

Only the data required for the notification system should be stored.

### Test production behavior separately from test endpoints

Temporary test endpoints should not remain in the final production
Worker.

### Versioning

When creating or replacing HTML files, always change the visible version
number in the footer so the currently loaded version can be identified
visually.

### File workflow

For code changes, use the existing file as the base whenever possible
and replace the same file in GitHub rather than creating unnecessary
duplicate versions.

## 14. Automatic cleanup of dead user IDs (25.09.2026)

Deleting and re-adding the Home Screen app wipes its local storage, so the
reinstalled app gets a NEW `userId`/`deviceId`. The old ID stays in KV and
its push subscription no longer works.

The Cron now cleans this up by itself:

-   Push returns 404/410 on **all** of a user's devices → the user's
    `pool:`, `done:`, `enabled:` and `subscription:` keys are deleted and
    the ID is removed from `users:index`.
-   User is enabled but has **no** subscription left → the ID is only
    removed from `users:index` (data kept).
-   Any later `/subscribe`, `/go`, `/pool` or `/done` call re-adds a user
    to the index automatically.
-   `users:index` is updated in one write at the end of each Cron run.

Known limitation: after a reinstall the pool for the next day was stored
under the old ID, so the new ID gets its first notifications only after
Wortschatz is finished once on the reinstalled app.

Backup of the previous Worker: `notification-server/src/index_before-cleanup.js`.

## 15. Notification ID in Backup / Restore (Home v5.20, 25.09.2026)

The Backup file now contains the anonymous `userId` (module
`notificationUser`). The `deviceId` is NOT included — it stays unique per
device. The ON/OFF switch is not included either.

On Restore, if the backup's `userId` differs from the device's current one:

-   the restored `userId` replaces the local one (Wortschatz uses it too);
-   if Notifications are ON on this device, Home re-registers the device's
    existing push subscription under the restored `userId` (`/subscribe`),
    enables that user (`/go`) and detaches the device from the old
    `userId` (`/unsubscribe`). The old ID is then removed by the Cron (§14);
-   if that fails, the local switch is set to OFF and Restore shows
    "Restored · turn Notifications on again";
-   if Notifications are OFF, nothing else happens; turning them ON later
    uses the restored `userId`.

Workflows:

-   **Reinstall:** make a Backup before deleting the app → reinstall →
    Restore → turn Notifications ON.
-   **Second device (iPad):** Backup on iPhone → Restore on iPad → turn
    Notifications ON on iPad. Both devices then share one pool, one DONE
    and one ON/OFF state.

Backups made before v5.20 contain no `userId`; restoring them leaves the
device's current ID unchanged.
